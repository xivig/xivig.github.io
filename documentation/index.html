01 — GET STARTED

Quick start

Run these commands from the repository root to start working locally.

TERMINAL
git clone https://github.com/xivig/xivig.github.io.git
cd xivig.github.io
npm install
npm run dev

Open the local URL printed by Vite in your terminal. Do not assume a fixed port: Vite may select the next available port if its default is occupied.

1CloneGet the source repository.
2InstallInstall dependencies with npm.
3DevelopRun Vite and edit source files.

03 — ARCHITECTURE

Project structure

The repository separates page entry points, shared frontend source, static files, and build automation.

 xivig.github.io/
 ├── app/
 │   ├── pages/              # HTML page entry points
 │   └── src/
 │       ├── partials/       # Shared Handlebars partials
 │       ├── scss/           # Sass styles and design tokens
 │       ├── scripts/        # ES module application logic
 │       ├── images/         # Source image assets
 │       └── plugins/        # Local plugin source/vendor files
 ├── public/                 # Static files copied by Vite
 ├── resources/views/        # Laravel Blade examples/templates
 ├── resources/laravel/      # Sample Laravel routes
 ├── tasks/                  # Build and validation scripts
 ├── documentation/         # This documentation site source
 ├── dist/                   # Local generated build output
 ├── docs/                   # GitHub Pages deployment output
 ├── index.html              # Main dashboard entry point
 ├── vite.config.js
 └── package.json

dist/ and docs/ are generated output directories. Make changes in source folders and regenerate the build instead of editing generated files.

04 — DEVELOPMENT

Development workflow

The project uses Vite for the development server, module processing, and hot reload. Gulp tasks are available for selected asset workflows; the production pipeline is orchestrated by tasks/build.js.

Start the dev servernpm run dev
Build with the full pipelinenpm run build
Build with Vite onlynpm run build:vite
Validate generated links/assetsnpm run lint:links
Preview Vite outputnpm run preview

Use npm run build before opening a pull request that changes pages, scripts, styles, or assets. It also exports the result for GitHub Pages.

05 — PAGE AUTHORING

Pages & templates

Top-level index.html and HTML files under app/pages/ are Vite entry points. Shared layout fragments live in app/src/partials/.

Adding a page

  1. Create the page in the appropriate category under app/pages/.
  2. Reuse the shared head, navigation, and layout partials used by neighboring pages.
  3. Keep page-specific scripts and styles scoped to the page where practical.
  4. Run npm run build and inspect the generated page in dist/.
  5. Check navigation, assets, responsive behavior, keyboard use, and console errors.
Routing note

The build flattens page HTML files into the output root for static-host compatibility. Avoid duplicate HTML basenames in different source folders; the current Vite entry discovery is based on file names.

06 — STYLING

Styles & design tokens

Styles are authored in Sass under app/src/scss/. Shared variables and design tokens should be preferred over page-specific hard-coded values.

app/src/scss/
 ├── base/          # Reset, typography, variables, tokens
 ├── components/    # Reusable UI components
 ├── layout/        # Header, sidebar, page shell
 ├── pages/         # Page-specific styles
 └── utilities/     # Helpers and utility classes

When changing brand colors, review both light and dark themes, hover/focus states, chart colors, and text contrast. Keep token definitions centralized and test normal text against WCAG AA contrast targets.

07 — INTERACTIONS

JavaScript

Application scripts are organized as ES modules under app/src/scripts/. Core initialization and shared behavior should remain separate from individual app modules.

  • Use textContent or DOM node APIs for untrusted text; avoid interpolating user-controlled values into innerHTML.
  • Register event listeners in JavaScript rather than adding inline event-handler attributes.
  • Handle loading, empty, success, and error states for asynchronous operations.
  • Do not store authentication tokens, secrets, or sensitive personal information in localStorage.
08 — ASSETS

Assets & plugins

Put authored images in app/src/images/ and public files in public/. Vite copies public assets into the build output. The build script also synchronizes source images and attempts WebP generation.

Vendor dependencies are declared in package.json. The build script copies a selected set of packages into dist/plugins/ to support the static output. If adding a plugin, verify its license, import only the files required, and update the build copy list if runtime URLs expect a copied vendor asset.

09 — BUILD PIPELINE

Production build

The full build is orchestrated by tasks/build.js. Its high-level sequence is:

01Clean stale output
02Compile with Vite
03Copy and optimize images
04Flatten HTML pages
05Copy required vendor packages
06Normalize links and export to docs/
07Validate local links and assets

Run npm run build. A successful run should finish with zero broken local links and assets. The generated site is in dist/; the GitHub Pages artifact is in docs/.

10 — DEPLOYMENT

GitHub Pages deployment

The repository includes .github/workflows/deploy.yml. On pushes to main or master, GitHub Actions installs dependencies, runs the production build, and deploys the docs/ output using GitHub Pages Actions.

  1. In the GitHub repository, open Settings → Pages.
  2. Set the publishing source to GitHub Actions.
  3. Push a tested change to main or master, or run the workflow manually from the Actions tab.
  4. Wait for the Deploy to GitHub Pages workflow to complete.
Documentation URL

After deployment, open https://xivig.github.io/documentation/. If the repository is deployed under a project subpath or a custom domain, use that site's base URL followed by /documentation/.

Do not edit generated docs/ files directly. Edit documentation/ and let the workflow copy the source into the deployment artifact.

11 — QUALITY

Quality checks

The current built-in checker validates local anchors and common local asset references in generated HTML. It is useful, but it is not a replacement for browser, accessibility, or security testing.

Before merging

Run the production build and inspect the changed pages at desktop and mobile widths.

Accessibility

Check keyboard navigation, visible focus, form labels, image alternatives, zoom, and color contrast.

Runtime

Check browser console/network errors, interactive flows, and external service dependencies.

12 — BACKEND INTEGRATION

Laravel integration

The repository contains Blade templates and a sample routes file under resources/. These are frontend integration references, not a complete Laravel application.

  • Move reusable Blade layouts and partials into a single canonical view structure.
  • Move compiled assets into Laravel's public asset pipeline (Vite or the deployment approach used by your app).
  • Replace demo forms and localStorage behavior with authenticated Laravel routes and validated requests.
  • Implement authorization policies, CSRF protection, server-side validation, database persistence, and audit logging.
  • Use Laravel's password hashing and authentication stack; never implement authentication only in browser JavaScript.

For a production application, integrate the UI into a fresh Laravel project and treat the sample routes/views as starting points only.

13 — SECURITY

Security notes

Demo interactions are not security controls.

Client-side visibility, localStorage, and static forms do not enforce identity or permissions. Every protected operation must be authorized by the server.

  • Do not send real or private files to demo upload endpoints. Connect uploads to your own authenticated backend, validate content and size server-side, and scan files where appropriate.
  • Escape untrusted output and avoid unsafe HTML injection.
  • Use HTTPS, CSRF protection, secure session cookies, rate limits, and server-side authorization.
  • Review dependencies regularly and pin external resources; use Subresource Integrity where suitable.
14 — SUPPORT

Troubleshooting

Vite says the default port is busy

Vite can automatically select another available port. Use the exact local URL printed in the terminal.

A page works locally but not on GitHub Pages

Check path casing, relative asset paths, generated output, and whether the latest Actions deployment succeeded. GitHub Pages hosting is case-sensitive.

A plugin's CSS or JavaScript is missing after build

Confirm the dependency is installed, the page references the expected output path, and the package is included in copyVendorPackages() if it is loaded as a copied static file.

Build validation reports a missing asset

Check the referenced path and filename case. Make sure the source asset is included by Vite or copied into the output before link validation runs.

Can I use the static GitHub Pages site as an admin backend?

No. GitHub Pages serves static files. Use a backend service or integrate the frontend into an application such as Laravel for authentication, data storage, and protected operations.
